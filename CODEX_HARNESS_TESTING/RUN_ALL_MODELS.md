# Run all samples with all image history

Run these commands yourself from the repository root. Each model uses low
reasoning, all image history, up to 20 decisions per sample, and the same saved
logging. All samples means every direct sample folder in the all-layers release
corpus. The inspected run contains 400 samples.

If you have not signed into the CLI, first run:

```sh
codex login
```

## Luna

```sh
bash CODEX_HARNESS_TESTING/run_luna_low.sh --image-history all --samples \
  $(find workspace/corpus/out/release/all-layers/samples \
    -mindepth 1 -maxdepth 1 -type d -exec basename {} \; | sort)
```

## Terra

  $(find workspace/corpus/out/release/all-layers/samples \

Run each command when you are ready for that experiment. Results are saved in
separate timestamped folders under `CODEX_HARNESS_TESTING/runs/`. CLI/service
errors stop a batch; the commands attempt all samples but do not guarantee
completion if an error occurs. Add `--max-turns 40` to change the decision
budget, and record that change when comparing runs.

## What all images means

Every invocation attaches the initial CP, target views, initial sheet views,
and every earlier feedback image generated by successful edits or `get_images`.
Rejected folds leave the state unchanged and generate no new images. The last
state's images remain attached. Each turn's `command.json` lists the actual
image arguments, and `images.json` records their labels and paths. Image input
grows with the episode and can reach service/context limits.

## Interpreting rejected actions

- `OUTSIDE_TARGET_CP`: the proposed fold introduces a crease segment or
  mountain/valley assignment absent from the supplied crease pattern.
- `ENGINE_REJECTED`: no new crease, the line misses the paper, or a crease
  direction conflict prevents the fold.
- An unchanged `state_id` after rejection is expected. Rejected actions do not
  modify the candidate.
- `tool-call flood` is an observability warning at 15 proposed calls. It does
  not mean the service failed or impose a 15-call limit.
- Repeating the same action at the same complete state more than three times
  stops the episode. Different invalid actions can continue until the turn
  budget; the controller does not automatically backtrack on the model's behalf.

Repeated rejections indicate stalled planning. They do not by themselves prove
that the simulator is wrong or that floating-point arithmetic caused a failure.
An accepted prefix can also require backtracking; acceptance only establishes
local crease compatibility, not that the remaining target can be reached.
